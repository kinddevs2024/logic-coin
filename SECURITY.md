# Политика безопасности Logic Coin

## Поддерживаемые версии

До первого стабильного релиза исправления безопасности применяются только к актуальной ветке разработки. Публичная эксплуатация MVP с реальными выплатами не поддерживается.

## Как сообщить об уязвимости

Не создавайте публичный issue с exploit, токеном, персональными данными или способом обхода начислений. Используйте GitHub Security Advisory: **Security → Advisories → Report a vulnerability** в репозитории проекта.

В сообщении укажите:

- затронутый commit/версию;
- минимальные шаги воспроизведения;
- ожидаемое и фактическое поведение;
- возможное влияние;
- безопасный proof of concept без чужих данных.

Подтверждение получения целесообразно дать в течение 3 рабочих дней, а статус первичной оценки — в течение 7 рабочих дней. Срок исправления зависит от критичности.

## Секреты

- `.env` и файлы ключей не коммитятся.
- MongoDB URI, SMTP password, OAuth client secret, JWT/session secret и Telegram
  bot token являются backend-only секретами. Android keystore и его пароли
  доступны только release CI.
- Любая переменная `EXPO_PUBLIC_*` встраивается в приложение и доступна пользователю.
- Для GitHub Actions используются GitHub Secrets/Environments, для Vercel — Project Environment Variables.
- Логи не должны содержать пароли, access/refresh tokens, коды подтверждения, полный URI базы или персональные платёжные реквизиты.
- Любой credential, опубликованный в чате, issue, commit, build log или клиентском bundle, нужно немедленно отозвать и перевыпустить. Простого удаления из последнего commit недостаточно.

Для проверки истории перед публикацией рекомендуется secret scanner (например, Gitleaks) и GitHub secret scanning.

## Аутентификация и данные

- Пароли хешируются современным password hashing алгоритмом и никогда не восстанавливаются.
- Email-коды одноразовые, имеют короткий TTL, хранятся в виде хеша и защищены rate limit.
- Одноразовый `registrationToken` хранится только в виде хеша, требуется вместе
  с email-кодом и удаляется после успешной проверки. Повторная незавершённая
  регистрация инвалидирует предыдущий token.
- OAuth callback проверяет `state`/PKCE и использует точный allowlist redirect URI.
- Access tokens короткоживущие и привязаны к активной серверной session. Refresh
  tokens ротируются, повторное предъявление заменённого token отзывает всю
  refresh-family, а logout инвалидирует связанную session.
- API валидирует входные данные, ограничивает размер body, настраивает CORS по allowlist и не доверяет идентификатору пользователя из тела запроса.
- Endpoint удаления аккаунта в текущем MVP не реализован. До его добавления
  необходимо определить и протестировать политику удаления/анонимизации данных.

## Награды и вывод

Клиент не может самостоятельно менять баланс. Начисление выполняется сервером атомарно, с idempotency key и журналом операций. До подключения рекламы MVP endpoint задания разрешает тестовое мгновенное начисление; в production его необходимо заменить серверной проверкой signed rewarded-ad callback.

Перед реальными выплатами обязательны:

- защита от replay, ботов, нескольких аккаунтов и гонок запросов;
- неизменяемый ledger вместо вычисления баланса из клиентских событий;
- ручной/автоматический antifraud review;
- лимиты и мониторинг аномалий;
- KYC/AML, налоговая и юридическая проверка применимых стран;
- платёжный провайдер и webhook с проверкой подписи;
- постоянный Android signing key и защищённый release pipeline.

Заявка на вывод в MVP не должна автоматически переводить реальные средства.

## Зависимости и сборка

- Lock-файл обязателен; CI устанавливает зависимости через `npm ci`.
- Dependabot/аналог должен регулярно проверять npm и GitHub Actions.
- Release APK из CI подписывается постоянным PKCS#12 keystore, который не
  хранится в репозитории. GitHub Secrets:
  `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
- Один и тот же signing key обязателен для обновлений уже установленного
  приложения. Нужна отдельная зашифрованная резервная копия keystore и паролей;
  потеря ключа может заблокировать обновления вне механизма Play App Signing.
- Текущий CI artifact предназначен для проверки MVP. Для публикации в магазине
  отдельно настраиваются AAB, versionCode/versionName, Play App Signing и
  release-процесс.
